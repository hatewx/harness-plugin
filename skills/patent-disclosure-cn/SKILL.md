# 中国专利交底书

把作者的发明材料蒸馏成代理师可审核、事实可追溯、技术链完整的交底书。保持三层分工：作者决定发明事实和技术边界；AI 展开、对齐并暴露缺口；专利代理师处理权利要求、法律判断和申请。

## 开始前

1. 读取 [中国规则基线](references/china-rules.md)。涉及软件、算法、AI 或商业规则时，再读取 [软件与 AI](references/software-ai.md)。需要检索或整理证据时，读取 [事实与检索](references/evidence-search.md)。
2. 识别当前任务阶段：`立项问诊`、`框架梳理`、`交底书起草`、`审校修订` 或 `代理交接`。不要强迫用户从头重来。
3. 优先读取用户提供的原始材料。材料不足时继续生成可用的部分成果，把缺口集中列入待确认清单；只有缺失会改变核心发明方向的决定时才立即提问。
4. 用户要求创建文件时，复制 `assets/` 中需要的模板。默认把同一发明的文件放在一个目录，不覆盖既有版本。

## 最小发明事实门槛

只有同时具备以下 F1/F2 内容，才进入技术方案、系统、实施例或完整交底书起草：

1. 一个具体技术场景中的技术问题；
2. 至少一个区别于已知做法的处理、结构或组件协作关系；
3. 该区别关系的输入、处理和输出；
4. 能从该区别关系合理归因的技术效果或作用机制。

若用户只有目标、营销概念或“用 AI 实现 X”的想法，使用 [发明澄清模板](assets/invention-intake-template.md)，只交付立项快照、公开风险、已有事实、缺口和集中问题。不要替作者生成带新机制的题目、完整步骤、系统、公式、实施例或拟保护特征。F5 只能扩展已有的 F1/F2 核心发明，不能代替核心发明。此门槛高于用户“直接写完整交底书”的形式要求。

## 不可突破的门槛

- 不把推断、检索所得启发或 AI 建议写成已经实现、验证或观察到的事实。
- 不编造实验数据、性能提升、参数范围、用户反馈、代码行为、发明人贡献或公开日期。
- 不因为需要三至五个发明点而机械扩写；只保留材料支持或作者确认的发明点。
- 不把专利摘要或二手概述当作完整的新颖性、创造性证据。不能阅读全文时，只标记为初筛线索。
- 不承诺“可授权”“不侵权”或“必然享有宽限期”。把法律结论交给代理师。
- 不直接替作者决定申请人、发明人、专利类型、保护范围或专利与商业秘密取舍。
- 不提前公开尚未申请的核心方案。若发现论文、演示、销售、开源、投标、会议或客户交付等潜在公开，立即标红并建议尽快交代理师判断。

## 事实状态

在工作表和审校记录中给每项关键技术内容标记状态：

- `F1 作者确认`：作者明确陈述为真实设计或实施。
- `F2 材料支持`：可定位到代码、图纸、实验、日志或研发记录。
- `F3 合理推断`：根据 F1/F2 推导，但尚未确认。
- `F4 待确认`：信息缺失或互相冲突。
- `F5 建议方案`：为增强公开充分性提出的候选实现。

交底书正文只把 F1/F2 作为确定事实。F3 使用条件化表达并列入确认项；F4 留占位或降级为缺口；F5 放入“可选补充方案”，作者确认后才能升级。记录每项 F2 的材料定位。

## 工作流

### 1. 建立立项快照

收集或推断后标记以下内容：发明名称暂定稿、技术领域、发明人及贡献、申请人候选、是否职务发明、首次完成时间、已有申请和优先权、所有潜在公开事件及日期、当前实现成熟度、可提供材料、是否容易从产品外部识别侵权。

发现公开或权属风险时，先输出风险和缺失事实，仍可继续技术梳理，但不得替代代理师判断。

### 2. 固定题目三板斧

分别写清：

1. 谁在什么具体场景遇到什么技术问题；
2. 已知做法如何处理，以及可验证的不足；
3. 本方案以什么核心技术链解决，区别落在哪里。

生成一句内部“灯塔句”：`针对[场景中的技术问题]，通过[核心技术手段/协作关系]得到[可归因技术效果]`。若只能写成“采用 AI 提高效率”，继续拆解，不进入完整起草。

### 3. 构造最小可实现技术链

把方案分为二至六个阶段；复杂方案使用阶段加子步骤。每个阶段都填写：

- 输入：来源组件、内容和格式；
- 处理：动作、规则、算法或部件协作关系；
- 输出：内容、格式和去向；
- 技术难点：传统做法为何不足，本步骤的差异是什么；
- 依据：F1—F5 状态及材料定位；
- 异常与边界：失败条件、缺失输入、阈值边界或降级路径。

检查相邻步骤：后一步的每个输入必须来自前一步输出、外部输入或已定义组件。禁止无来源的 `A+B`。

### 4. 从步骤反向提取系统

只从技术链提取系统组件、数据对象和组件关系。为每个组件记录功能、输入、输出、对应步骤、事实状态及其为公知基础还是拟保护改进。

逐项双向检查：步骤使用的组件必须存在；组件必须至少被一个步骤使用。删除数据库、缓存、网络等未参与技术效果的装饰性基础设施；若其机制本身是改进点，则写出具体协作关系。

### 5. 建立支持矩阵和实施例

为每个拟保护特征建立：问题依据、结构或步骤依据、实施例依据、技术效果依据、替代实现、待确认项。至少构造一个从真实输入到真实输出的端到端实施例。

优先补充能防止不当限缩的内容：等价部件、步骤顺序变体、参数确定方法、范围端点、异常路径和组合方式。不能从材料得出时，作为 F5 建议，不得伪装为事实。

### 6. 处理现有技术

先固定发明事实，再制定检索式。围绕必要特征和区别特征检索，不围绕营销名称检索。记录数据库、日期、检索式、文献号、公开日、命中特征和证据位置。

分别做单篇文献的新颖性初筛与组合文献的创造性风险分析；清楚区分二者。不要为了突出发明而推测背景文献没有写明的“缺点”。把未核验结论标为待代理师复核。

### 7. 生成交底书

使用 [交底书模板](assets/disclosure-template.md)，按“技术领域—背景技术—发明内容—系统组成—方法步骤—实施例—附图建议—效果依据—替代方案—待确认项”展开。默认以清晰完整为先，不追求申请文件式法律语言。

正文要求：

- 技术效果必须能归因到具体区别特征；没有数据时写机制性效果，不写百分比。
- 公知算法或标准可先给通行名称，再说明本方案如何配置、连接或改进；不要用一个名词代替实现过程。
- 名词、编号、输入输出和步骤顺序全篇一致。
- F3—F5 不混入确定性正文；保留清晰的审阅入口。

### 8. 审校和交接

从 Skill 目录运行：

```bash
python3 scripts/validate_disclosure.py <交底书.md>
```

再按 [质量门槛](references/quality-gates.md) 做人工语义检查。失败项不要隐藏：修复能从材料修复的内容，其余进入 `待确认事项.md`。

使用 [代理交接模板](assets/agent-handoff-template.md) 汇总核心发明、拟保护层次、材料索引、检索状态、公开和权属风险、事实缺口以及希望代理师决定的问题。明确标注交底书不是权利要求书。

## 交付规则

- 先交付可审核的 80% 工作稿，不为形式完整牺牲真实性。
- 修改时给出“修改项—依据—影响”，避免静默改动发明边界。
- 保留版本号和日期；重大边界变化新建版本。
- 把问题分为 `阻断起草`、`影响保护范围`、`代理师判断`、`可后补`，集中提问。
- 完成标准：技术链无跳跃、步骤与系统双向一致、关键特征有依据、至少一个可实现实施例、风险与缺口显式、代理师能据此继续工作。
