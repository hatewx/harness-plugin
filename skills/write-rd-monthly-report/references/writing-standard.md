# 研发经营月报写作标准

## 1. 核心取向

月报首先回答“这个月具体做成了什么”。使用版本、功能、指标、交付物、评测结果和真实截图建立可信度，不用“赋能业务”“形成闭环”“放回经营坐标”等套话替代事实。

经营表达来自事实的选择和产品映射，不是额外增加一章价值解释。不要创建“从技术成果到产品与经营成果”章节。

## 2. 推荐结构

### 一、核心摘要

- 使用一个绿色提示块写“快速总结”。
- 写 4–6 条本月最重要的真实变化，例如 OKR 对齐、技术立项、客户项目验证、产品发布形态、基础设施规格化。
- 摘要之后使用三列表格：`技术线 | 本月关键结果 | 产品落点`。
- 除非状态是管理者当前需要判断的信息，不要为表格机械增加“状态”列。

### 二、技术进展

按最新技术体系组织。每条技术线：

1. 引用对应技术调研页。
2. 使用加粗结果句开头。
3. 补充具体功能、版本、指标和验证情况。
4. 在合适位置插入真实截图。

默认归类参考：

| 技术线 | 常见内容 |
|-|-|
| 空间数字化 | 空间重建、SpaceBuilder、空间或实体管理、场景编辑、CAD、BIM、模型资产 |
| 空间原位交互 | 3Top、大场景、坐标与渲染、Trigger、相机、图层、Agent Interaction、Operational Twin |
| 空间智能体系开发 | SpatialSmart、Fabulous Agent、DigitalNative Agent、Skill、Harness、评测链路、应用开发 |
| 工程基础 | LLM Gateway、测试覆盖、MR 门禁、发布部署、资源包、监控告警、用量与成本 |

这张表只是检查清单。最终归类必须以最新技术体系和当月实际工作为准。

把“重点项目支撑”作为技术进展中的最后一个二级小节，使用 `项目或产品 | 本月进展 | 状态` 表格。项目内容应说明技术验证或复用，不展开日常需求流水账。

### 三、风险、决策与协同请求

只写当月仍存在、需要管理动作的风险。没有证据时不要沿用上月风险。用简短列表即可；不要为了完整性制造红色提示块。

### 四、下月重点计划

按 PFT 或产品、技术线和项目复用组织。每项使用待办，写可识别的目标，例如“支持 929 示例应用开发”“CAD 文件导入预研”，避免“持续优化”“加强协同”。

## 3. 事实密度

优先保留：

- 明确产品版本或发布形态，如 Web 版、测试包版本、插件版本。
- 明确功能清单，如 Side Chat、文件拖拽、预算管理、Session Trace 聚合。
- 明确指标，如用例数、覆盖率、评测得分、性能规格。
- 明确技术资产，如 Skill、Plugin、Harness、Benchmark、测试门禁。
- 明确产品或项目验证，如 Honeywell 对 Operational Twin 的验证。

减少或删除：

- 没有数据支撑的“重大突破”“行业领先”。
- 重复解释“为什么重要”的段落。
- 仅描述未来可能性的技术设想。
- 为了整齐而补出的状态、风险或经营结论。

## 4. 术语与产品映射

- 保持公司文档中的大小写和正式名称。
- 使用“评测”描述 eval，不混用“评估”。
- 使用 `DataSet`、`Evaluator`、`Skill`、`Plugin`、`Harness` 等团队实际采用的技术术语时保持一致。
- 产品映射写到 MSPU 或组件层级；不要只写模糊的“PFT 产品体系”。
- 所有 Harness 能力应说明通过 Omni 版本化时，需有仓库、版本或发布记录支撑。

## 5. 图片规则

图片必须承担证据功能，优先级如下：

1. 产品功能或发布界面。
2. 评测结果或错误分布。
3. 插件或版本管理记录。
4. 用量、性能或质量指标看板。
5. 客户项目真实效果。

每张图放在对应事实之后。图注说明“图中展示什么结果”，不要使用装饰性概念图，也不要让截图替代正文结论。

## 6. 语言与排版

- 研发风格：结论短、名词准确、数据充分。
- 用加粗引导句组织段落，不把每个小点升级成标题。
- 一段只表达一个结果簇；功能清单可用分号或短列表。
- 保留必要英文技术名，不做生硬中文化。
- 核心摘要可使用绿色提示块；其他颜色仅在真实风险或状态需要时使用。
