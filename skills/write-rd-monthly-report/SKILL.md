# 撰写研发经营月报

以管理者修订后的月报为风格基准，把部门真实完成项整理成按技术线组织、与产品体系直接关联、可核验的经营月报。

## 必读资料

开始前完整读取：

- [写作标准](references/writing-standard.md)：结构、归类、措辞和截图规则。
- [资料路由](references/source-routing.md)：飞书资料入口和取证顺序。

同时按任务调用对应的飞书技能：读取或编辑正文使用 `lark-doc`，搜索周报使用 `lark-drive`，解析部门人员范围时使用 `lark-contact` 或通讯录原生接口。

## 工作流

### 1. 确认口径

确认“月报名称月份”和“实际报告周期”。例如 8 月经营月会可能汇报 7 月工作，不能自行按自然月推断。

读取目标文档最新版本。若已有管理者修订，保留其标题层级、术语、内容取舍和图片，不用旧草稿覆盖。

### 2. 建立证据台账

在写正文前，从报告周期内的个人或部门周报、研发会议周报、项目记录和产品资料提取：

| 字段 | 要求 |
|-|-|
| 完成项 | 已完成、已上线、已发布、已验证或已交付的具体结果 |
| 证据 | 版本号、覆盖率、用例数、评测分数、功能清单、文档或截图 |
| 技术线 | 按最新技术体系判断，不沿用旧月报的错误归类 |
| 产品落点 | 使用产品体系中的准确 SPU、MSPU 或组件名称 |
| 状态 | 只写来源明确的完成度、风险或阻塞 |
| 来源 | 保存周报、项目文档或截图所在链接，便于回查 |

禁止把计划、讨论、调研意向写成已完成结果。不同来源数字冲突时，使用更新且更接近原始产出的来源，并说明口径。

### 3. 按技术线归类

先读取最新技术体系，再归类。不要只按项目名或团队分工排列。

默认检查四条线：空间数字化、空间原位交互、空间智能体系开发、工程基础。技术体系变更时以最新文档为准。

把重点项目支撑放在技术进展之后作为同章小节，避免另起“从技术成果到经营成果”之类的空泛章节。

### 4. 映射产品体系

只建立有直接证据的映射：

- 使用 `HARP`、`Foundation`、`Tellus`、`Artemis`、`DevEssen`、`SpatialSmart`、`SpaceBuilder`、`3Top`、`LLM Gateway` 等最新正式称谓。
- 优先写“产品或 MSPU → 技术组件”或产品文档采用的层级关系。
- 不为了显得有经营价值而强行关联产品；无法确认时先查产品体系或向用户确认。

### 5. 写正文

遵循 [写作标准](references/writing-standard.md)，优先写：

1. 快速总结：本月真实发生的 4–6 项关键变化。
2. 技术线结果表：技术线、本月关键结果、产品落点。
3. 技术进展：每条技术线先给技术调研链接，再写具体版本、功能、指标和截图。
4. 重点项目支撑：只保留可说明技术复用或产品验证的项目。
5. 风险、决策与协同：只写当前真实风险。
6. 下月计划：使用明确的产品、技术线和交付目标。

### 6. 编辑飞书文档

编辑前按 `lark-doc` 要求读取最新正文和编辑规范。

- 用户要求整篇重写时才使用全文覆盖。
- 用户已经修改过文档时优先局部编辑，避免丢失其修订、引用和图片。
- 保留文档中的 `cite`、图片、附件、画板和其他资源块。
- 图片使用真实产品、评测、版本、用量或交付界面，并写清它证明什么。

### 7. 验证

写入后回读文档，至少检查：

- 标题层级与技术线顺序正确。
- 所有数字、版本和完成度能回到来源。
- 技术线与产品落点没有错位。
- 没有套话、重复价值解释或未证实的经营结论。
- 图片已成为有效文档资源块，图注与正文一致。
- 风险和下月计划没有混入已完成事项。

## 输出要求

向用户说明修改位置、主要变化、已验证项和仍需确认的缺口。不要只说“已优化”。
